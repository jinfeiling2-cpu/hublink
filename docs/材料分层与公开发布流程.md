# 材料分层与公开发布流程

记录时间：2026-10-26

这份记录把收集箱里新出现的简历、计划、创意和思想材料放进 Hublink 的工作方式中。它们可以属于同一个人的资料网络，但不能因此混成同一种内容，也不能因某个项目有公开页面就自动公开它的所有细节。

## 当前材料的判断

目前还没有证据表明游戏和长篇创作已经做成可运行、可试玩或已发布的作品。现有文件支持的是“提出过什么设想、如何拆解和讨论”，不能支持已完成项目、产品成果或用户反馈等说法。

因此，游戏和创作材料先作为个人创意档案保存。Hublink 将来可以把经确认的概念作为一种公开阅读对象，但必须清楚标为构思、策划或原型等实际阶段；是否放进公开首页或简历由本人决定。

## 五种不能混为一谈的判断

| 判断 | 它回答什么 | 例子 |
| --- | --- | --- |
| 材料类别 | 这份内容是什么？ | 简历、证明、研究计划、游戏设想、世界观、讨论记录 |
| 工作阶段 | 这件工作做到哪一步？ | 构思、已整理方案、原型、测试、发布、停止 |
| 内容来源 | 谁提出或确认了这句话？ | 本人原文、本人确认的整理、AI 建议、外部证明、待核实推断 |
| 发布范围 | 谁可以看到这一项内容？ | 个人、待本人审核、公开、撤下或归档 |
| 阅读方式 | 读者想从什么角度进入？ | 简历、项目概览、设计拆解、时间线、学习记录、AI 资料包 |

这些判断彼此独立。比如，一份“游戏构思”可以处于“已整理方案”阶段，来源中包含 AI 建议，发布范围仍是“个人”；一个公开项目也可以有私人内部资料。

## 项目公开程度怎样落到内容上

项目的公开程度是对项目内容的整理目标，不是自动传递给所有组成部分的权限。可以有以下层次：

```text
项目的公开概览
  ├── 公开：题材、核心问题、本人确认的一句话介绍
  ├── 待本人决定：玩法细节、设计取舍、选定的局部设定
  └── 个人：原始草稿、私人讨论、未采纳建议、完整证据附件
```

每个可独立阅读的部分都应能单独决定是否发布。公开项目的页面只展示已经确认公开的子项；把一个项目的简介设为公开，不等于原始策划、对话、附件和私人想法也公开。反过来，原始资料保持个人，也不妨碍另行写出一份不包含私密细节的公开简介。

当前 Hublink 只有节点级 `public` / `personal` 可见性，没有正文段落或附件级权限。因此短期做法是把公开简介、个人分析和原始资料分开放：公开节点只写可公开内容，私人部分放在个人文件或独立的个人节点中，不在同一段正文里混写。公开连线也只连接两端均已公开的节点。以后确有反复需要，再评估区段级权限和发布历史；本轮不改数据库模型。

## 从原件到公开内容

```text
个人原件
  -> 个人整理稿
  -> 公开候选稿
  -> 本人核对内容、作者归属、证据和公开范围
  -> 独立的公开条目或节点
```

个人原件保留为来源，不直接作为网站正文。公开候选稿应当能脱离原件独立阅读；发布前核对：

- 事实、时间、角色和成果状态是否准确；没有证据的部分是否明确写为构思或待确认。
- 本人原话、本人接受的整理、AI 建议和外部事实是否分清。
- 是否含有私人联系方式、第三方信息、未公开计划或不准备公开的创作细节。
- 公开内容是否会让读者误以为构思已经实现，或把某条建议误认为作者定稿。

当前文件整理阶段把原件视为个人资料；正式内容只在本人确认后进入公开节点。以后如果后台增加“待审核”流程，它应是发布状态；不能拿项目的“构思中 / 已发布”等工作阶段代替发布权限。

## 本批材料的处理方式

| 材料 | 原件处理 | 可能的公开版本 | 当前边界 |
| --- | --- | --- | --- |
| 简历 | 留在个人收集箱，作为核对来源 | 经本人确认字段和联系方式后，制作公开简历与 AI 结构化资料 | “有简历来源”不等于原文件本身可以直接放到公开仓库 |
| 实习证明 | 作为个人证据附件保存 | 通常只公开本人确认的经历描述和必要的证明出处 | 不公开证明原件；证明内容不自动推出职责或成果 |
| 研究规划与远景附录 | 保留个人原文，按承诺层级整理 | 另写当前研究简介、已确认方向或单独文章 | 长期计划、私人约束和推测远景不自动进入简历 |
| 游戏构思 | 按创意档案整理，标记构思阶段和实现证据 | 本人选择后可发布短简介、设计文章或局部方案 | 当前材料不能写成已完成游戏或已验证产品 |
| 世界观与小说框架 | 保留设定版本、空白和建议来源 | 可选择发布作品简介、主题说明或部分设定 | AI 建议和候选设定不等于已接受的正典 |
| 长期讨论档案 | 作为个人思考和学习来源保存 | 选取并重写为可独立阅读、经事实核查的文章 | 对话全集不是定稿立场，也不是默认公开材料 |

## 文件夹怎样配合这套流程

当前五个主目录按材料用途整理，不代表公开权限：

- `01-简历与履历/` 保存简历来源和履历证据。公开的是经过确认的简历整理稿，不一定是这里的原文件。
- `02-个人规划/` 保存研究计划、个人路线和远期思考的来源稿。
- `03-项目与经历概述/` 留给有实际项目或经历信息的材料。当前没有已完成的游戏作品，因此不把游戏构思放入这里冒充项目成果。
- `04-目标与关注问题/` 留给目标、问题和待回答事项。
- `05-其他材料/` 目前按内容再分为 `游戏构思/`、`世界观创作/`、`思想讨论/`。这是当前归档位置，不是永久分类标准；后续可以根据资料量再调整。

目录是找资料的方式，不是发布开关。收集箱整体保持 Git 忽略；公开站只使用经过本人核对并明确选择公开的整理结果。

## 对框架的暂定影响

Hublink 需要分别回答“这是什么”“做到哪一步”“依据从哪里来”“能不能公开”“如何阅读”。当前模型已有节点类型、工作状态、来源快照与节点级可见性，可以先通过案例文档验证这些边界，不急着把所有概念加进数据库。

后续用简历、一个真实项目、一份创意档案和一篇思想条目走一遍流程，再评估是否需要增加作者归属、确认状态、证据等级、发布审核或局部可见性。新增字段只有在不同材料中都解决实际问题时才进入正式模型。
