# Hublink：搭建规划与理解记录

这份文档先把两件事分开记录：当前代码实际做了什么，以及下一版准备解决什么。代码能证明页面、数据流和已有功能；个人动机、贡献、成果和学习收获，需要由项目参与者补充，不能从代码里推断。

关于多种阅读者、简历生成验证、AI 结构化读取和共同学习的新增目标，另见 [多读者与简历验证设计记录](多读者与简历验证设计记录.md)。当前先保存设计判断；载入更多项目、经历和产出资料后，再进行第二波模型和界面调整。

## 要搭建的东西

Hublink 面向两个使用者。访客需要看懂一个人的工作、方向、经历和作品；项目参与者需要把这些材料连起来、解释清楚，并在梳理过程中形成自己对工作的认识。

因此，内容先组成一张完整图谱，再由不同阅读方式取出其中一部分。概览可以提供简历式阅读；关系图、时间、规模、重要性、联系和三维坐标适合比较；项目、经历和社交账号可以沿着组成关系继续展开。每个项目应同时说明它要解决什么、由什么构成、怎样运行、参与者做了什么，以及从中形成了什么认识。

线上网站应同时提供公开阅读和个人管理。访客只能读到公开内容；管理员可以在网页后台新增、修改、连接、隐藏和发布内容。GitHub 仓库保存应用代码、数据库迁移、说明和可迁移的数据导出，不承担线上数据库的职责。

## 当前项目能证明什么

当前仓库已经有一个可运行的图谱原型，代码实现了节点、连接、分类、公开过滤、多种预设阅读方式、后台写入和 GitHub 仓库元数据拉取。现有设计说明在 `docs/框架说明.md`，节点和关系种子在 `src/content/hublink.ts`。

当前项目还没有个人履历、其他作品、公开部署或真实读者效果。内置 Hublink 节点主要说明代码目录与部分调用路径。它可以作为第一个“正在建设的软件项目”案例，用来测试项目结构图、运行图和讲解内容；现有材料不足以把它写成已经验证成功的个人代表作。

从代码可以读出的系统结构是：

```text
访客阅读
  Next.js 页面或公开 API
    -> SQLite store 读取公开节点与两端公开的连接
    -> domain 函数进行过滤、排序、遍历或计算坐标
    -> React 组件显示关系图、列表或三维网格

管理员写入
  后台表单
    -> server action 检查登录
    -> Zod 校验表单
    -> SQLite store 创建或更新节点、连接和类别
    -> 重新验证页面缓存

GitHub 同步
  后台提交仓库地址
    -> GitHub API 读取仓库元数据、README 摘录和根目录
    -> mergeSourcePull 保留人工编辑字段并更新来源快照
    -> SQLite store 保存
```

主要代码职责如下：

| 部分 | 当前职责 |
| --- | --- |
| `src/app/` | 阅读页、节点详情、框架页、公开 API 和后台路由 |
| `src/domain/registry.ts` | 节点、连接、度量、类别、阅读方式和来源登记 |
| `src/domain/graph.ts` | 公开过滤、排序、印象选取、遍历、坐标和来源合并 |
| `src/domain/schema.ts` | 后台节点表单校验和解析 |
| `src/db/store.ts` | 在 SQLite 中读写节点、连接和类别 |
| `src/lib/github.ts` | 通过 GitHub API 拉取仓库快照 |
| `src/lib/session.ts` | 以签名 cookie 识别后台会话 |
| `src/components/` | 关系图、三维网格和编辑表单 |

目前的阅读方式是预先写在 `src/domain/registry.ts` 的配置中，页面根据类型选择渲染方式。读者可以查看关系图、简历式印象、若干排序、三维网格，以及项目、经历、社交账号的向下遍历。后台能新增节点和连接，但还不能创建新的阅读方式。

本轮新增 `/project/hublink` 案例页，将系统职责、访客阅读、管理员写入、GitHub 同步、Git 提交中可确认的搭建顺序和待回答的学习问题放在一处。首页也改为显示公开图谱数量；之前曾把个人节点数量一并显示，这会泄露私人内容的存在数量，现已移除。

可见性目前是节点级别的 `public` / `personal`。公开查询只读取公开节点，公开连接要求两端都是公开节点。GitHub 来源快照中的 README 摘录和根目录不会进入公开 API；其他来源信息会经过 `publicSnapshot()` 筛选。

## 当前实现的边界

- SQLite 文件位于运行进程的 `data/hublink.sqlite`。这适合本地原型；部署到无持久磁盘的 serverless 环境时，不能把它当作长期数据库。
- 登录目前依赖一个共享口令和签名 cookie，适合开发验证，线上版本应接入可靠的身份验证和管理员白名单。
- 节点正文主要集中在简介、角色、结果和一段说明中，不能自然表达项目的背景、架构、运行、取舍、证据和个人反思。
- 阅读方式是开发者登记的预设项；“概览”若仅靠分数自动选取，无法保证表达的是参与者真正想让读者记住的内容。
- `centrality` 当前由编辑者填写，并没有从关系图计算。它需要一个更明确的名称和判断标准；自动算出的连接数量也应与人工判断的个人重要性分开。
- 连接类型已经登记，但后台对节点类型之间的连接组合约束有限。图可以保存关系，读者仍需要关系解释才能理解一条线为何存在。
- 当前 Hublink 内部图较多从目录和函数出发。它有助于开发者定位代码，不足以成为普通读者理解产品、也不足以帮助项目参与者理解系统设计的主要路径。
- 仓库代码不能说明参与者的实际分工、接受或否决过哪些 AI 建议、项目结果是否达到目标，以及哪些知识已经真正掌握。

## 第一个项目案例：Hublink

Hublink 适合先作为结构试验案例。代码覆盖公开阅读、领域规则、存储、后台写入、来源同步和图形展示，因此能够验证新框架是否同时说得清“系统由什么组成”和“系统如何工作”。

项目页可以组织为以下几段：

1. **项目概况**：要服务谁、当前要解决什么问题、项目处于什么阶段。
2. **系统结构**：阅读端、图谱规则、内容存储、管理端、外部来源和图形展示分别承担什么职责；说明关键依赖关系。
3. **实际运行**：以“访客打开一张关系图”“管理员编辑节点”“同步一个 GitHub 仓库”为例，逐步说明输入、处理和结果。
4. **关键判断**：例如为什么区分公开节点与个人节点，为什么 GitHub 快照不覆盖人工撰写的说明。代码可以证明现在的行为，判断当时的原因仍需参与者确认。
5. **参与者的工作**：谁提出目标、谁整理需求、哪些代码由 AI 辅助生成、哪些实现经过阅读和修改、哪些部分尚未掌握。具体归属待确认。
6. **结果与证据**：当前可核对的证据包括仓库代码和本地验证：9 项测试通过、Lint 通过、生产构建成功。它们证明工程检查通过，不等同于有访客使用或产品目标已经达成。
7. **个人理解**：哪些概念已经能够独立解释，哪些设计仍有疑问，下一步如何通过实际修改或讲解检验理解。由参与者撰写或确认。

项目结构图与运行图应分别回答不同问题。结构图以职责和依赖为主；运行图以一次操作中的先后步骤为主。源码文件和函数名可以作为可展开的技术证据，放在概念解释之后。

## 下一版内容与图谱模型

图谱中每个节点代表一个可单独阅读的对象，例如项目、方向、经历、账号、文章、能力、组织或项目中的一个部分。节点之间的连接表达清楚的关系，例如“由……组成”“依赖……”“在……期间发生”“产出……”“记录……”或“体现……”。重要连接可以有一句理由或证据，不能只靠线条和关系名传递意义。

项目节点至少需要支持这些内容：

- 一段面向访客的概况，以及项目状态。
- 背景、问题、目标、参与者职责、做法和结果。
- 由项目部分组成的结构图，以及这些部分怎样协作。
- 可排序的运行步骤，必要时标明输入和输出。
- 重要决定、放弃的方案、证据和外部链接。
- 参与者的理解、疑问和后续学习记录。

这些内容不要求每个项目填满所有栏目。简短项目可以只写概况和结果；复杂项目再添加结构、过程和反思。代码仓库目录可作为证据链接，不应自动等同于项目架构。

度量和类别分开处理。日期、规模、人工评定的重要性或个人关联度可以用于排序与坐标；图谱连接数量等事实由程序计算。方向、主题、成果形式、角色等可以是可筛选的分类，也可以在需要解释关系时升格为图谱节点。每个度量都要有清楚含义和使用说明，尤其要区分个人判断的关联度与程序计算的连线数量。

阅读方式是对同一图谱的一组展示规则：

- **概览 / 简历**：由参与者明确选择和排序，不以自动分数代替个人判断。
- **关系图**：按主题、对象类型或关系筛选，并沿关系阅读。
- **时间、规模、重要性、联系**：使用定义明确的度量排序或分组。
- **三维坐标**：读者选择三个有意义的维度；坐标缺失时清楚标示。
- **项目阅读**：切换结构、运行、决定、结果和个人理解等路径。
- **经历与社交阅读**：从经历到片段、产出，或从账号到条目和作品。

第一版阅读方式应保持少而清楚。每种方式都要说明它展示了什么、如何选择节点，以及它能回答什么问题；以后再从实际使用中增加视图。

## 目标部署架构

为了支持网页在线管理，建议保持 Next.js 全栈应用，把线上数据放在托管 PostgreSQL。推荐先评估 Vercel 部署 Next.js、Supabase 提供 PostgreSQL 与认证；GitHub OAuth 或其他受支持登录只授权指定管理员。具体供应商在部署前再核对价格、区域、备份和账号策略。

```text
公开访客
  -> Next.js 阅读网站
  -> 服务端公开查询
  -> PostgreSQL 中的公开节点和连接

管理员
  -> 网站后台
  -> 身份验证与管理员授权
  -> 服务端写入和发布操作
  -> PostgreSQL

GitHub
  -> 保存代码、迁移、文档与可迁移导出
  -> Actions 负责测试和部署
  -> GitHub API 提供仓库元数据
```

线上后台编辑不需要依赖本地电脑。开发时仍可在 WSL 中修改代码、运行测试和预览；它只是开发环境，不是内容管理的唯一入口。

发布规则需要覆盖所有输出：页面 HTML、公开 API、搜索索引、关系图、统计、缓存、站点地图和预览元数据。公开查询只返回公开节点和两端可公开的连接；个人内容留在服务端，并由受保护后台读取。修改可见性后要更新公开页面和相关缓存。数据库应有备份，并提供可恢复的数据导出。

当前的节点级可见性可以保留作第一阶段基础，并补上“草稿”与“归档”状态。若确实需要一个公开项目内包含私密部分，再增加子节点和内容区段级别的发布控制；不应一开始就把每个字段都拆成多种可见性，避免后台难以使用。

GitHub Pages 是静态托管，没有持久在线数据库，也不能直接承载安全写入后台。若未来希望公开站使用 Pages，可以从数据库导出公开数据并生成静态版本；不把它作为当前在线编辑架构的核心。

## 实施顺序与验收

### 阶段一：项目理解与内容规范

- 确认 Hublink 的目标读者、当前问题、项目阶段和参与者分工。
- 按结构、运行、决定、证据、个人理解重写这个项目的说明。
- 将每句文字标明为代码事实、外部事实、参与者判断或待补充信息。
- 找一位不熟悉代码的人试读，记录他能否说清系统用途和基本流程。

### 阶段二：新图谱模型和项目阅读样例

- 明确节点、连接、度量、类别、内容区段和发布状态的含义。
- 把项目结构图与运行图做成可读、可展开的阅读界面。
- 把“概览”改为人工选择和排序。
- 先用 Hublink 验证，再选一项内容形态不同的作品检查模型是否过度贴合软件项目。

### 阶段三：在线管理与安全发布

- 设计 PostgreSQL 表结构和迁移；编写 SQLite 到新格式的导入/导出工具。
- 接入管理员登录和授权，所有写操作只在服务器执行。
- 为公开查询建立统一入口，避免不同页面各自实现可见性过滤。
- 检查个人数据不会出现在页面源代码、API、搜索、缓存或静态资源中。
- 支持预览、发布、归档、备份和恢复。

### 阶段四：完整网站与公开内容

- 完成概览、图谱、维度浏览、项目深读、经历和社交阅读。
- 加入搜索、移动端体验和来源证据。
- 在发布前确认公开内容和个人内容清单。
- 在真实使用后再决定是否增加更多维度、关系或阅读方式。

验收不以节点数量或图形复杂度为准。访客应能理解项目为什么存在、参与者做了什么、结果如何、系统怎样工作；参与者应能在线维护图谱、解释关键关系，并确认私密信息没有进入公开输出。

## 已知事实与待确认问题

从仓库和测试可确认：

- 项目使用 Next.js、TypeScript、SQLite、Zod、d3-force 和 Three.js。
- 当前图谱种子把 Hublink 项目组织为应用页面、领域规则、数据库、工具函数、交互组件，以及读取、写入、GitHub 拉取路径。
- 公开过滤、排序、图遍历、来源合并等规则有单元测试。
- Git 历史显示，图框架与后台先建立，之后加入公开过滤、首次项目节点、按颜色聚类的关系图，再把内部图改为代码框架和文件路径。

下列内容不能从代码确定，后续写成公开介绍前需要参与者确认：

- Hublink 最初由谁提出，实际面向的对象是谁。
- 项目参与者分别承担了哪些设计、实现、审核和学习工作。
- 当前最重要的产品问题是什么，哪些问题已经解决，哪些仍未解决。
- 是否有目标用户试用、实际反馈、使用数据或其他结果证据。
- 哪些设计决定来自参与者，哪些由 AI 提议，哪些仍未理解或未验证。
- “规模”“重要性”“个人相关性”等维度最终采用什么定义和标尺。

在得到这些信息之前，项目文字应使用“当前代码实现了……”和“计划支持……”等可核实表达，不写“成功帮助用户……”一类没有证据的结果。
