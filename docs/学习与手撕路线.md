# Hublink 学习与手撕路线

这是一份给第一次读完整 Web 项目的人准备的操作手册。目标不是背文件名，而是能从一次真实操作说清：用户做了什么、系统经过哪些部分、数据如何变化、结果为什么这样显示，以及哪里还不安全或未完成。

学习时一次只追一条功能路径。先猜它怎么工作，再找证据，最后自己讲一遍并做一个小改动。遇到不懂的术语，先记下来；不要求第一遍全部弄懂。

## 开始前：你要学会什么

Hublink 同时包含五类问题：

1. **产品问题**：它想帮谁整理什么材料？读者为什么会使用不同浏览方式？
2. **内容问题**：什么是节点、连接、度量、分类和公开状态？
3. **程序问题**：页面、规则、数据库、后台和外部 API 怎样分工？
4. **安全问题**：个人节点怎样留在后台，公开页面为什么看不到它？
5. **工程问题**：怎样运行、测试、修改和部署？当前版本离线上网站还缺什么？

先记住这个区分：**结构图讲每部分负责什么；运行图讲一次操作按什么顺序经过这些部分。** 两张图解决不同问题。

## 系统地图

### 访客打开关系图

```text
浏览器打开 /view/network
        |
        v
Next.js 页面：src/app/view/[id]/page.tsx
        |
        +--> SQLite store：读取公开节点和连接
        |
        +--> domain/graph.ts：筛选、整理图谱数据
        |
        +--> lib/network.ts：准备绘图所需的数据
        |
        v
NetworkGraph 组件：在浏览器里画出并操作节点与连线
```

### 管理员编辑节点

```text
后台表单
   -> server action 检查管理员会话
   -> Zod 检查输入格式
   -> SQLite store 写入节点和类别
   -> 重新验证相关页面
```

### 同步 GitHub 仓库资料

```text
后台提交仓库地址
   -> 服务端请求 GitHub API
   -> mergeSourcePull 合并来源快照与人工撰写内容
   -> SQLite store 保存
```

这三条路径共用一部分规则和数据保存方式，但入口、检查和结果不同。在线 PostgreSQL、正式管理员登录和部署还没有完成，不能把目标架构当作当前功能。

## 先把项目跑起来

在 WSL 终端进入项目并选择 Node 22：

```bash
cd /home/jinfeiling/hublink
source "$HOME/.nvm/nvm.sh"
nvm use 22
npm run dev
```

保持这个终端打开，在浏览器访问 `http://127.0.0.1:43123`。这是本机开发站点。关掉运行开发服务器的终端后，站点会停止。

后台入口是 `/admin`。README 里列有本地原型的开发口令。它只用于本机学习，不是公开部署可用的登录方案；在后台创建或修改数据会写入本地 SQLite 文件。

要停止开发服务器，在运行它的终端按 `Ctrl+C`。不要为了“重置”而直接删除数据库；先确认里面有没有自己要保留的内容，并在做破坏性实验前备份。

## 学习循环：每个功能都这样拆

每次花 30 到 60 分钟，只挑一个问题。

1. **观察**：在网页里做一个动作，准确记下看到什么。
2. **预测**：在读代码前，写下你猜数据去了哪里、系统做了什么。
3. **追踪**：从页面入口往下读，标出输入、处理、输出和错误处理。
4. **复述**：合上代码，用自己的话画图或讲给别人听。
5. **修改**：只改一个小行为，运行相关检查。
6. **核对**：比较预期和实际，说明结果是由哪段规则造成的。

读不懂时先问“这个函数收到了什么、返回了什么、谁调用它？”比先问“这个文件是什么意思？”更容易定位。

## 分阶段手撕

### 第 1 阶段：理解产品和现在的边界

先读：

- `README.md`
- `docs/搭建规划与理解记录.md` 的“当前项目能证明什么”“当前实现的边界”和“目标部署架构”
- `docs/框架说明.md`
- 网站里的 `/project/hublink`

浏览首页、简历概览、关系图、三维网格和项目深入。每个页面记下三件事：它展示什么、它使用什么数据、它不能证明什么。

自测：

- 当前版本有哪些功能能在本机实际操作？
- “本机 SQLite 原型”和“在线个人主页”差在哪里？
- Hublink 案例页哪些话是代码事实，哪些问题还需要你本人回答？

### 第 2 阶段：看懂目录和基本数据

从这些文件开始：

- `src/domain/types.ts`：程序里的节点和连接有哪些字段？
- `src/domain/registry.ts`：系统登记了哪些节点类型、连接、度量、分类和浏览方式？
- `src/content/hublink.ts`：第一个案例怎样写入节点和连接？
- `src/domain/schema.ts`：后台表单输入如何被检查？

把一条节点记录和一条连接分别画成小卡片。字段可分为：身份（id、标题、类型）、说明（简介、正文）、时间和度量、可见性、出口链接。连接要能回答：从哪个节点到哪个节点，关系叫什么，为什么这样连？

自测：

- “项目属于某个方向”适合写成节点字段、分类还是连接？为什么？
- “联系数量”和“个人关联度”由谁决定？前者由连接数量计算，后者是编辑者判断。
- 项目的架构部分和运行步骤为什么可以成为独立节点？

### 第 3 阶段：追访客阅读路径

先追关系图这一条：

1. `src/app/view/[id]/page.tsx`：页面拿到的路由 id 是什么？它怎样选择浏览方式？
2. `src/db/store.ts`：节点和连接从哪里读出？
3. `src/domain/graph.ts`：`visibleGraph`、`rankNodes`、`traverseTree` 等规则分别处理什么？
4. `src/lib/network.ts`：为什么要把应用里的节点转换成绘图数据？
5. `src/components/network-graph.tsx`：浏览器如何画点、线、选择状态？

追踪过程中不要把“数据库读数据”和“React 画图”混为一件事。前者负责拿到记录，领域规则负责解释记录，组件负责把结果变成能看的界面。

自测：

- 用户点选一个圆时，哪些内容会变化？哪些数据没有变化？
- 一个没有任何连线的公开节点会不会被数据库删掉？
- 若要改变圆的颜色，应该先找数据规则还是绘图组件？

### 第 4 阶段：验证公开与个人的边界

重点阅读：

- `src/db/store.ts` 中带可见性条件的读取
- `src/domain/graph.ts` 的 `visibleGraph`
- `src/app/api/graph/route.ts`
- `src/domain/graph.test.ts` 中公开过滤相关测试

在本地后台新建一条测试节点，分别切换为个人和公开，再检查首页及 `/api/graph`。注意个人节点与公开节点相连时，那条连接也不能出现在公开结果里。

自测时检查三个出口：页面、API、统计或图形。不能只看页面没有显示；还要检查浏览器的网络响应或直接打开 API，确认个人数据没有返回给浏览器。

### 第 5 阶段：追管理员写入

重点阅读：

- `src/components/node-form.tsx`
- `src/app/admin/actions.ts`
- `src/lib/session.ts`
- `src/domain/schema.ts`
- `src/db/store.ts`

从点“保存”开始，一步步回答：表单送出哪些字段？谁检查管理员身份？谁检查字段范围？谁执行写入？保存后页面如何知道要刷新？

自测：

- 如果没有登录，在哪一步被挡下？
- 如果重要性超出 0 到 1 的范围，在哪一步报错？
- 为什么组件不直接打开 SQLite 写数据？

### 第 6 阶段：追 GitHub 同步

重点阅读：

- `src/app/admin/actions.ts` 中来源同步动作
- `src/lib/github.ts`
- `src/domain/graph.ts` 中 `mergeSourcePull`
- `src/domain/graph.test.ts` 中来源合并测试

重点观察“外部事实”和“人工叙述”的边界。仓库名称、简介、语言等可以从 GitHub 更新；你的角色、结果、理解和可见性不能被同步覆盖。

自测：

- 第一次拉取会创建哪些字段？
- 再次拉取哪些字段会更新，哪些保留？
- GitHub README 为什么不能代替你对项目的说明？

### 第 7 阶段：看懂浏览方式和图形

分别对照：

- `src/domain/registry.ts` 中的 `views`
- `src/app/view/[id]/page.tsx` 中按 `view.kind` 分支渲染的逻辑
- `src/components/network-graph.tsx`
- `src/components/axis-view.tsx` 与 `src/components/axis-canvas.tsx`

先理解同一份节点数据如何按不同规则排序或筛选，再看它如何被画成圆点、连线或三维坐标。浏览方式改变的是呈现和取舍；除非有保存操作，它不应该悄悄改变节点本身。

自测：

- 增加一个“按时间排序”的浏览方式，哪些规则可以复用？
- 增加一种全新的图形时，哪些情况才需要新组件？
- 重要性、规模和个人关联度为什么不能混成同一个分数？

### 第 8 阶段：读测试、做改动、确认理解

常用命令：

```bash
npm test
npm run lint
npm run build
```

- `npm test` 检查当前脚本覆盖的领域规则和案例内容规则；它不是完整的浏览器端到端测试。
- `npm run lint` 检查代码风格和常见错误。
- `npm run build` 检查生产构建、类型和页面生成。

按由浅入深完成这些练习，每次只做一题：

1. 改一个可见文案，确认它在哪个文件定义、在哪个页面出现。
2. 给一个领域规则补测试，再故意改错实现，观察测试怎样失败。
3. 新建公开和个人测试节点，核对页面与公开 API 的差别。
4. 给某个项目添加一个架构部分和一条关系，让它出现在“项目深入”中。
5. 设计一种新的浏览方式：先写它要回答的问题，再确定排序或筛选规则，最后接上页面。
6. 画出线上版本需要替换的部分，并解释数据库、登录、备份、缓存分别负责什么。

每完成一个练习，查看 `git diff`，确认改动只有自己预期的内容；跑对应测试；再用浏览器验证结果。

## 怎样判断自己真的掌握了

一个功能达到“掌握”，至少可以做到四件事：

- 不看 AI 或教程，画出用户动作到结果的路径。
- 说出每一层的职责，并说明为什么不能随意把职责混在一起。
- 找到一条测试或亲手设计一个测试来验证规则。
- 做一个小改动，预测会影响哪里，再用运行结果验证自己的预测。

读过文件、听懂解释或看到页面能运行，只代表接触过；能预测、解释、验证和改动，才说明知识开始属于你。
