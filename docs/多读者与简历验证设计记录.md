# 多读者与简历验证设计记录

记录时间：2026-10-22

这份记录保存当前阶段对 Hublink 目标的进一步理解。它先记录方向、参考方式、验证顺序和待确认问题，不立即把所有设想改成代码。等载入更多项目、经历和产出资料后，再进行第二波调整。

## 一、当前新增的目标

Hublink 不只是个人主页或关系图。它要把同一套经过整理、可以核对的个人材料，提供给不同的阅读者和不同的阅读深度：

1. **个人总结与思想构建**：帮助参与者整理自己的工作、方向、经历、产出、决定、疑问和学习成果，并在整理过程中形成对自己的理解。
2. **外来者的简历式阅读**：让不了解参与者的人先获得清楚、准确、篇幅适中的基本印象，知道其身份、方向、代表工作、角色和当前状态。
3. **外来者的深度探索**：让读者进入项目结构、工作过程、经历转折、产出来源、关键决定和相关证据，逐步建立完整理解。
4. **AI 的结构化读取**：让负责整理简历或回答问题的 AI 获得一份明确、稳定、可引用的资料，而不是只依赖视觉图形或从零猜测网页含义。
5. **个人、读者与 AI 的共同学习**：把“已经确认的事实”“参与者的判断”“仍需核实的内容”“学习中的问题”分开记录，使人和 AI 都能在同一份材料上继续修正理解。

这几个目标应该来自同一份内容基础，再生成不同的阅读结果。简历、网页、深度项目页、AI 资料包和学习文档不应各自维护一套互相矛盾的内容。

## 二、最重要的判断：先验证简历生成

当前 Hublink 已经能展示图谱、节点、连接和若干浏览方式，但还没有用真实的个人材料生成一份经过检验的简历。因此，复杂图谱是否真正帮助别人理解一个人，目前仍然没有得到验证。

下一阶段应先回答一个更急迫的问题：

> 从一组真实的项目、经历和产出资料出发，系统能否生成一份准确、清楚、适合人阅读，也适合 AI 继续读取的简历？

在简历生成验证完成前，不应继续增加过多新的维度、动画或图形。图谱有价值的前提，是它能支持准确的基本说明。

简历验证至少检查这些内容：

- 身份、方向、时间和状态没有被错误合并。
- 每个项目都能显示参与者的角色，而不是只显示项目名称。
- 结果和证据分开，不能把“代码通过测试”自动写成“已经成功解决用户问题”。
- 未确认的个人贡献不会被 AI 或模板补写成事实。
- 公开内容与个人内容在简历、网页、API、搜索和导出文件中保持一致。
- 同一份输入重复生成时，基本内容和排序稳定可解释。
- AI 读取到的是结构化字段和来源，而不是只能从图形位置猜测含义。

## 三、适合外来者和 AI 的共同内容基础

每个项目、经历或产出应有一份可独立阅读的“案例档案”。共享字段可以保持一致，具体章节根据对象类型增减。

### 共同字段

```text
标题和对象类型
一句话概述
时间和当前状态
背景与问题
参与者和角色
工作内容
结构或组成
过程和里程碑
关键决定
结果
证据与来源
限制与未解决问题
个人理解与学习记录
相关项目、经历、方向和产出
可见性和发布状态
```

### 项目

项目重点说明问题、系统结构、运行过程、角色分工、决定、结果和证据。复杂项目可以再展开架构部分、运行步骤、决策记录和代码出口。

### 经历

经历重点说明时间和环境、承担的角色、关键转折、完成的工作、产生的产出，以及这段经历怎样影响后来的方向。经历不能只是机构名称和日期的列表。

### 产出

产出重点说明作品本身、面向的对象、使用场景、形成过程、迭代或反馈、原始链接，以及它和项目或经历的关系。

每个章节不必全部填写。短项目可以只有概况、角色、结果和出口；复杂项目再增加结构、过程和决定。空缺应该明确显示为“尚未记录”，不能由系统猜测补齐。

## 四、四种阅读结果

同一份案例档案可以生成四种主要结果。

### 简历阅读

给普通读者使用。顺序应当稳定，先给身份、方向、代表项目、经历和结果，再提供继续深入的链接。它要像一份清楚的简历，但不应丢失项目之间的关系。

### AI 简历资料

给简历生成、问答和资料整理 Agent 使用。它应有稳定的字段、清晰的类型和来源，例如：

```json
{
  "title": "项目名称",
  "type": "project",
  "time": { "start": "YYYY-MM", "end": "YYYY-MM" },
  "role": "待参与者确认",
  "summary": "经过确认的一句话说明",
  "outcomes": [],
  "evidence": [],
  "related": [],
  "confidence": "confirmed|self_reported|inferred|open",
  "visibility": "public|personal"
}
```

这不是要求现在立即采用这个 JSON 格式，而是说明 AI 读取需要一种比网页视觉结构更稳定的出口。AI 不能把页面中出现过的每句话都当成同等可信的事实。

### 深度探索

给希望理解项目或个人工作方式的读者和 AI 使用。它应能沿着背景、结构、过程、决定、证据和反思继续走，并显示每条关系为什么存在。

### 共同学习

给参与者、读者和 AI 一起使用。它需要区分：

```text
代码或外部资料直接确认的事实
参与者明确说明的个人经历
参与者对事实的解释
系统根据关系得到的推断
尚未回答的问题
```

“学习与手撕”文档属于这一层。它不是项目宣传文案，而是帮助人和 AI 共同建立正确理解的学习材料。

## 五、历史和证据怎样进入阅读

Git 提交、Issue、Pull Request、Release、测试和文档都可以作为材料，但它们的意义不同：

- Git 提交可以证明代码何时发生变化。
- Release 可以说明某个版本增加了什么。
- Issue 和 Pull Request 可以保留问题、讨论和方案比较。
- ADR 可以记录技术选择、备选方案和后果。
- 测试可以证明某条程序规则在给定输入下成立。
- 参与者的说明才能确认实际角色、动机和学习收获。

原始历史不应该直接变成读者需要阅读的提交列表。系统应把它整理成里程碑、决定、证据和反思，再链接回原始材料。

每个重要结论最好采用“结论—证据—状态”的形式：

```text
结论：当前版本实现了公开节点过滤
证据：src/domain/graph.ts、src/app/api/graph/route.ts、相关测试
状态：代码确认
```

```text
结论：参与者独立完成了某个关键设计
证据：需要参与者补充的工作记录或说明
状态：待确认
```

## 六、值得借用的公开方法

这些项目和方法各自解决一部分问题，不应整体照搬：

| 参考 | 可以借用的做法 | 在 Hublink 中的作用 |
| --- | --- | --- |
| [GitHub README](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) | 先说明是什么、为什么存在、怎样开始 | 项目案例的入口和概览 |
| [C4 Model](https://c4model.com/) | 按层级解释系统结构 | 项目结构图和组件图 |
| [Architecture Decision Records](https://adr.github.io/) | 记录选择、备选方案和后果 | 关键决定和历史理由 |
| [Diátaxis](https://diataxis.fr/) | 区分教程、操作、参考和概念解释 | 区分简历、学习文档、技术参考和操作说明 |
| [Quartz](https://github.com/jackyzha0/quartz) | 双向链接、反向链接和图谱探索 | 深度探索和相关对象导航 |
| [Academic Pages](https://github.com/academicpages/academicpages.github.io) | 结构化的项目、论文和经历内容 | 长期维护的履历数据结构 |
| [HugoBlox](https://github.com/HugoBlox/kit) | 内容类型、Markdown 和发布流程 | 内容管理和页面生成参考 |
| [The Pudding](https://pudding.cool/) | 用叙事顺序和视觉证据带读者理解复杂主题 | 复杂项目的深度阅读方式 |
| [GitLab Handbook](https://handbook.gitlab.com/) | 公开记录组织原则、流程和历史 | 个人工作方法和长期历史记录 |

目前最值得采用的组合是：GitHub README 的入口、C4 的结构、ADR 的决定、Quartz 的关系、The Pudding 的叙事顺序，以及 GitHub 历史的证据链接。

## 七、第二波调整的触发条件

在载入更多资料后再调整，避免当前只根据 Hublink 这一个软件项目设计出过度贴合软件的模型。建议至少准备几种不同材料：

1. 一个软件项目。
2. 一个非软件项目或创作产出。
3. 一段真实经历及其中的关键片段。
4. 一篇文章、一次分享或其他可独立阅读的作品。
5. 一项有明确外部链接或证据的成果。

每项材料先按共同字段整理，不急着增加新的节点类型。载入后检查：

- 哪些字段对所有对象都有用。
- 哪些章节只适合项目，不适合经历或产出。
- 哪些关系在软件项目中成立，在其他材料中不成立。
- 简历概览是否能从这些材料中稳定生成。
- AI 读取时是否会把判断、推断和事实混在一起。
- 普通读者能否从概览进入深度阅读，又能否回到清晰的基本信息。

第二波调整的顺序建议是：

1. 先调整案例档案和简历字段。
2. 再调整项目、经历和产出的专用章节。
3. 再调整证据、历史和 AI 资料出口。
4. 最后调整图谱关系、排序、三维坐标和视觉表现。

## 八、当前不立即实施的内容

- 暂不把这份记录直接变成新的数据库表。
- 暂不根据单个 Hublink 案例确定最终节点类型数量。
- 暂不把图谱中的自动排序当成最终简历选择机制。
- 暂不声称已经能够生成正确简历；需要真实材料进行验证。
- 暂不声称 AI 能准确理解个人内在；需要明确来源、状态和人工确认机制。
- 暂不进入线上数据库、正式认证和公开部署改造。

当前阶段的完成标准是：资料被载入后，能够用一份真实案例生成一版简历、一版 AI 结构化资料和一版深度说明，并让参与者核对它们是否准确。只有这三种结果都能保持一致，才值得继续扩大图谱和在线功能。

## 九、待参与者补充的问题

- 哪些信息必须进入公开简历，哪些只用于个人学习？
- 你希望 AI 在读取个人资料时优先回答哪些问题？
- 哪些内容可以由代码或外部来源确认，哪些只能由你本人确认？
- 你希望别人如何描述你的角色、能力、方向和变化？
- 哪些经历或作品最适合先用来检验简历生成？
- 你希望“共同学习”记录保存哪些内容：疑问、解释、纠正、练习、决定，还是全部保存？
